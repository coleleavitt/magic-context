CK session extensibility: modules, presets and delivery

An explainer of design DRAFT r2 (with §6.2 R7–R9 and the §10 AFT presets), for the approve-or-revise decision. Nothing described here is built [D header]. Every claim cites its source; anything marked illustrative is an example written for this page, not taken from the sources. Where the sources left something unclear, a yellow “Gap found while explaining” box says so instead of filling it in; all of them are collected in §9.

1. The one-page picture

The problem

On 2026-09-25 Magic Context was run inside Broca masons. The work MC's OpenCode plugin does on its own (serve the ctx_* tools, write the guidance, reshape history) had no owner in Broca, so it leaked across three parties one chat-negotiated patch at a time [D §2]:

  • a tool_present flag so the transform knew whether its tools existed;
  • Prefrontal fetching MC's guidance text with guidance.get;
  • identity fields, cache-marker restore and field aliases.

The landscape shows the same shape everywhere [D §2, S §8–§10]: every host lets plugins add tools, guidance and transforms, but none separates appending from rewriting history (OpenCode #43507: a plugin using the supported hook silently killed cache reads), none lets a caller pick a bundle across plugins per session (plugins get an agent id and sniff), and none sandboxes plugin code. Each host also needs its own plugin rewrite, because what a session gets is decided inside each plugin, per host (MC's OpenCode and Pi plugins each infer “main vs subagent” themselves) [D §9].

Meanwhile providers now allow mid-conversation system messages that add operator text and add, remove or redefine tools at the end of history without touching the cached prefix, so the design must not assume guidance and tools change only on a full rebuild [D §2].

The model in one diagram

Eight principles carry the model [D §3]: one owner per session concern; consistent by construction (callers pick presets, never flags); modules say what, the host decides how; anything byte-affecting is frozen or written down; append is not rewrite; authority follows authorship; refuse by name, never degrade silently; hot path = data, cold path = code.

Principle 5 says “History rewrite is one exclusive, privileged slot” [D §3]. r2 then split history operations into one exclusive reduction owner plus an ordered pipeline of preserving stages [D §6.6, answering outside review #10]. This page follows §6.6: only reduction is exclusive. The principle's wording predates that split.

2. Concepts

Module

A running subc module, or an installed declarative extension file. A running module advertises capabilities.provides: ["ck.session-extension/v1"], so one catalog.list read finds every extension module, and serves its presets from extension.describe on its existing ManagementSurface [D §4, §5.2].

extension.describe →
{ "interface": "ck.session-extension/v1",
  "presets": [ ... ] }

No new manifest role: ProviderRole is closed for subc v1 and an unknown tag fails HELLO decode, so a new role would need a two-phase fleet rollout per schema change [D §5.1].

Preset

A named, versioned bundle of one module's contributions. No parameters: a variant is another preset (main-full, main-light). It declares requires_tools, replaces_slots, and its transform mode and interface if it reduces history [D §4, R1, R3].

illustrative syntax
{ "name": "subagent-readonly",
  "tools": ["ctx_expand", "ctx_search"],
  "system_text": "<read-only guidance, static>",
  "requires_tools": ["ctx_expand", "ctx_search"],
  "replaces_slots": [] }

The design names the fields but gives no concrete schema; “this room owns the schema” [D §5.2].

Contribution kinds

  • Tools: schemas plus the module that executes them; may replace a host built-in slot.
  • System text: module-written guidance, operator authority (needs a grant).
  • Reminders: short module-written text meant for one turn.
  • Reduction owner: the one component reducing history.
  • History pipeline stage: other history operations, which must preserve sent spans.
  • Provider notices: async results between turns; never operator authority.

[D §4]

Session class

A closed vocabulary owned by Prefrontal: head, worker, reader, panel, aggregator, oneshot. Delivered to every module at admission, so no module sniffs env vars or agent names. Modules never map themselves to classes; a persona declares which class it runs as [D §4, §6.1, R2].

illustrative
persona "explore" runs as: reader
→ table row "reader" decides the rest

Composition table

Lives in Prefrontal core; replaces today's three unconnected places (persona role base, agent.role_tool_permissions, per-project substrate). Each row: persona role, ordered presets (≤1 per module), reduction owner, history pipeline, class profile (a remove-only tool filter), operator-text grants. Overridable per project; a project names installed presets and never supplies one [D §4, §6, §6.1].

illustrative row
reader → role: explore
         presets: [mc:subagent-readonly, aft:delegated]
         reduction: mc   pipeline: []
         profile: −sidekick −athena −work
         grants: mc (static text)

Composition record

What one session actually got, frozen at admission: {class, persona role, [(module, preset, interface, contribution digest)], reduction owner, history pipeline, system-text order}. One digest over the resolved bytes (text and schemas as served), not names and versions, so a same-version restart with different text still changes it. That digest is the class 1 epoch for the whole prefix; the session inspector shows the record [D §7.2 step 4, R4]. Also frozen with it: user config such as disabled_tools (R8), the host adapter's declared tool additions (R7), and per-tool contract revisions (§7.2 step 6).

Reduction owner and preserving chain

Context reduction is exclusive per session: MC's transform, host compaction, or none. Other history operations (redaction) form an ordered pipeline around it and must preserve every span already sent. v1 ships the reducer only, but the record models a chain with one reducer, so adding a stage later is a new row, not a schema change [D §6.6, §7.7]. Where a need can be met at write time, plugin-hooks class 4 (“decorate once and persist”) is preferred [D §7.7, PH].

operator_message

A new WAL record: {module, epoch, scope: persistent | turn, text_digest, blocks: [text | tool_addition | tool_removal]}. Built only from granted static text, as the delta between frozen epochs. Written at the next legal position: after a user turn or tool results, never first, never between tool_use and tool_result [D §7.4].

illustrative
{ "module": "mc", "epoch": "e2", "scope": "persistent",
  "text_digest": "sha256:…",
  "blocks": [{"text": "<added paragraph>"}] }

provider_notice

{provider, notice_id, task_id, payload} for async results (AFT background tasks, MC Channel 2 wakes). notice_id is per event: stable across retries, distinct across events; idempotency on (provider, session, notice_id). The provider holds it until the host acks the fsync. One engine-wide size cap: oversized is refused with a typed error, never truncated. Renders as a marked user-role block on every family [D §7.4].

notice_id: task:<task_id>:exit
notice_id: task:<task_id>:match:<byte offset>

[D §10 AFT]

Host-only arguments

A property for the host, not the model, carries "x-ck-audience": "host" in its JSON schema (AFT's shell, foreground_orchestrate; AFT renames x-aft-consumer-only). The composer strips every such path, including nested, $ref targets and required entries. Dispatch rejects a model call containing one before host values are merged; the provider also rejects them on any route whose caller hasn't declared it supplies them [D §5.4, §7.6].

illustrative
"shell": { "type": "string",
           "x-ck-audience": "host" }

Declarative file extensions

A file in the same preset schema: system text, MCP tool sources, replaced slots. No process; applied as class 1 data. Counts only after an explicit user-level install (ck extension add or setup) that pins its digest; never discovered by scanning; mismatched bytes refused by name, never reloaded. A project may name installed extensions, never supply one: cloning a hostile repo must not install operator text [D §5.3].

The §10 “third-party persona (declarative file)” example is, in the design's own terms, a declarative preset carrying static system text only, pinned by digest and given an operator-text grant [D §10, OR]. Personas themselves belong to the caller (Prefrontal's persona catalog), not to extensions [OR].

Trust tiers

  • Operator text is granted per module and preset in the table, separate from discovery, and must be byte-identical to the bytes pinned at grant time [§6.3, §7.3].
  • Untrusted carrier: per-session values (repo name, count, recalled note) at user authority.
  • Modules: first-party full replies; third-party the restricted tier by default (text-only replies, project-root restriction, bash only after a host grant), no operator-text grant unless given; declarative: no code at all [D §8].
ContentAuthority
persona role, granted static guidanceoperator
module remindersoperator, one turn
per-session valuesuser (carrier)
tool results, notices, recalled memoryuntrusted

[D §8 table]

§8 says module tiers follow “AFT's existing split” (text-only replies, project-root restriction, bash after a host grant). Those are restrictions on what AFT's tools do for a low-trust caller. The design doesn't say what the restricted tier means for a third-party module's own process (pi-subagents, for example, spawns child processes; the coverage report maps it to “restricted tier” without saying what's restricted [C PI-1]). Isolation today comes from modules being separate processes behind subc [D §8].

3. The life of a session

One head session, illustrative but built only from mechanisms the design names. Table row: [mc:main-full, aft:interactive], reduction owner MC's transform, empty pipeline, on an Anthropic model with mid-conversation system messages.

Background notice		An AFT background command exits. AFT sends provider_notice{provider: aft, notice_id: task:<id>:exit, …} and holds it until Broca acks the fsync. 5
MC reduction		MC's transform, the exclusive reduction owner, reshapes history. The engine then checks every sent operator_message and provider_notice is byte-identical and in order, and the current turn is intact; a violation fails the step with a typed error [D §7.7]. Recalled memories and compartments stay in the transform's user-role rows [D §7.7, §10].The transform's own frozen replay, keyed on (session, input fingerprint, render config) [D §7.7, run.rs:2050].The transformed view.The design doesn't change how a reduction itself affects the cache; that remains the reducer's decision. What it adds: between reductions, frozen replay makes the view render identically, and protected spans can't be edited silently.
6
Upgrade activates		MC ships a release whose main-full text adds a paragraph. The session keeps e1 until Prefrontal activates the new composition at a run boundary (a turn start, for a head; never mid-task for a worker). That send's admission freezes e2 and writes the epoch change to the WAL [D §6.5, §7.2 step 5]. Dispatch keeps carrying each tool's pinned contract revision [D §7.2 step 6].Record e2 and its digest.In this row MC is not the last module (AFT follows it), so the change is one ordered rebuild of the system text at that send. An appended persistent operator_message is allowed only for an addition from the text that is last in precedence, host notes included, or for a turn reminder [D §6.4, §7.5].The append goes after the prefix. A rebuild costs one declared cache bust, never a silent one.
7
Resume after restart		Broca replays the frozen record and never calls extension.describe. Notices and operator messages come from the WAL. The transform is re-invoked, and its frozen replay should reproduce the view; Broca compares the re-rendered request digest with the recorded one [D §7.1, §7.2 step 5, §7.7]. A reader that finds a must-understand record it doesn't know refuses to resume the lineage, by name [D §7.4].Nothing new.A byte-identical request.Byte identity is the invariant (§7.1). A digest mismatch is logged and priced as a rebuild. Limit: the step that crashed may have no attempt record (no own fsync), so its resume is compared against nothing [D §7.7].
Who triggers step 6. The design says “Prefrontal decides when a session activates” [D §6.5]. Broca's plugin-hooks doc says “activation IS the module flipping its declared epoch for a session”, with no push RPC [PH, “Class-1 epoch activation”]. The coverage report raises the same conflict as Q1. This page follows the design and flags it.
Ordinary later sends (between steps 3 and 6). A send that activates nothing reuses the frozen record and makes no extension.describe call: “An existing session keeps its pinned record until an activation at a run boundary … Nothing activates implicitly on the next send” [D §6.5]; “A session keeps its frozen record until a send's admission activates a new one” [D §7.2 step 5]. So a module that is down doesn't block an ordinary send, because its contributions are frozen; a call to one of its tools still fails at dispatch with the usual tool error. describe is called only at first admission and at an activation Prefrontal chose. This matches plugin-hooks' “absent supplier proceeds on the lineage's frozen artifacts” [PH].
Assumption (not stated in the design): if the module is down at an activation, the activation doesn't happen, the session stays on its current record, and Prefrontal can retry at the next boundary.

4. The rules and why they exist

“Cost” is quoted where the design states it. Where it doesn't, the cost shown is derived, meaning read off the mechanism by this page, and marked so.

4.1 Consistency rules R1–R9 [D §6.2]

RuleFailure it preventsWhat it costs
R1 Presets are named bundles of contributions, no parameters; a variant is another preset.Callers combining flags into inconsistent bundles (principle 2: “the caller picks presets; it never combines flags”). The 2026-09-25 Broca run is the example: a tool_present flag patched between three parties [D §2, §3].Derived: the preset count grows with variants (MC declares five, AFT four) [D §10].
R2 Session class is a closed vocabulary owned by Prefrontal, delivered at admission.Modules sniffing context from env vars or agent names [D §6.1]. Seen in AFT's per-class description variants chosen by env-var sniffing, and in MC's plugins inferring main vs subagent [D §9, §10].Derived: a new kind of session needs a Prefrontal vocabulary change, not a module change.
R3 A preset declares requires_tools and replaces_slots. The class profile only removes tools. Removing a required tool refuses composition; the fix is a different preset, not harder filtering.A preset whose behaviour depends on a tool the class took away; MC's #519 permission probing and tool_present. Under R3, “a class whose profile denies ctx_reduce gets subagent-readonly” [D §6.2, §10].Derived: modules must ship a preset per restriction level, and the table author must pick them.
R4 One composition record per session, frozen at admission, one digest over the resolved bytes; shown in the session inspector.“What did this session get” needing more than one read; a same-version restart with different text going unnoticed (the digest covers bytes, not names and versions) [D R4, §7.2 step 4].Any byte change in any contribution is a new epoch, and so a declared change at the next activation [D §7.2 step 5].
R5 No module fetches another module's text; guidance.get goes away.The 2026-09-25 incident: Prefrontal fetching MC's guidance [D §2]. Principle 1: nobody re-derives or second-guesses a module's contributions.Derived: Prefrontal can't tailor MC's text; per-class text must be MC presets.
R6 One table serves every host; a part a host can't deliver is refused for that host by name.A preset meaning different bundles on different hosts, and silent drops (principle 7). MC's OpenCode and Pi plugins stop inferring main vs subagent and read the preset from the record [D §9].Each host lowers the record through its own mechanisms; OpenCode has no mid-conversation operator messages, so every change folds at the next rebuild [D §9].
R7 The tool set is closed under reference. Each tool declares static references; checked when the declaration is read and again at admission over the final set (presets + adapter additions, then trust, then user removals). The adapter's additions are written into the record.Observed 2026-09-26: AFT's flat catalog offered bash, whose reply names bash_status, without bash_status, so a Broca worker's follow-up call was refused [D R7]. A user removal can break closure too (disable bash_status, keep bash).Every tool must list references; each module keeps a test that rendered replies name only declared references; a preset needing an adapter-only tool is refused on Broca [D R7].
R8 Never part of a preset: trust (applied after, as a bound), user config (remove-only, frozen at admission), host capabilities (declared by the host; a preset states requirements and admission refuses or takes the table's fallback).A preset restoring a tool that trust removed [§7.3]; config changes mutating live sessions; presets probing their host. Example: AFT's bash.subagent_background config only made sense per session kind, so it moves into the preset [D §10].A config change “reaches new sessions only” [D R8].
R9 Presets come from the module's ck.session-extension/v1 query, never the HELLO manifest. A session with no record (hand-run CLI) gets the module's declared default preset, recorded as such; modules should default to their most restrictive preset.Growing the closed manifest role set (§5.1). An unrecorded caller getting primary-only behaviour [D R9].Derived: hand-run sessions get restrictive behaviour unless given a record. AFT maps the no-record default to oneshot [D §10].
Exclusive slots: context management, each replaced built-in, tool names. Double claims refused; collisions never renamed or ordered.Load-order conflicts the survey found in every host (plugins mutating one shared object; order between hooks mattering) [D §2, S §8].Derived: two plugins that both replace bash can't share a session.
Core class-profile rules: e.g. reader never gets sidekick, athena, work.Observed 2026-09-25: a read-only explore worker given those tools delegated its question straight back into sidekick [D §6.2].Rules no module can know live in core, not in presets.
§6.3 Operator text is a grant in the table, per module and preset, and must be static (byte-identical to the pinned bytes).Outside review #2: a module's own declaration proves who sent the bytes, not where the text came from [D §6.3].Per-session values lose operator authority and travel in the untrusted carrier; MC's date line and counts move out of the guidance [D §10].
§6.4 Fixed order persona → modules → host notes; append only when precedence can't change (last module's addition, turn reminder).Outside review #5: later operator text overrides earlier text, so an arbitrary append would reorder authority. “Removing a sentence from a preset really removes it” [D §6.4].A change from any module other than the last is an ordered rebuild at the next run boundary [D §6.4]. Host notes count as later text, since an append after them would outrank them and so “change precedence” (the rule's stated purpose). In practice, when host notes are present every module change is a rebuild and only turn-scoped reminders can be appended.
§6.5 Upgrades activate once, at a run boundary; workers finish on the record they started with.Outside review #4: conflicting upgrade lifetimes [D table, §6.5].A long-running worker keeps old behaviour until it finishes; modules must serve old contract revisions meanwhile (§7.7).
Host notes after module text (clarification for r3). §6.4 puts host notes after module text, then allows an append for “an addition from the last module in the order”. Read against its own purpose (“allowed only when it can't change precedence”), the rule must mean the last text in precedence order, host notes included; this page presents it that way. §6.4 should say “last in precedence, including host notes”.
§7.2's refusal list is incomplete. Step 3 lists seven refusals, but R7 (dangling reference, including after user removals) and R8 (unmet host capability without a fallback) also refuse at admission. Figure 1 and step 2 above include them.

Turn reminders: three statements that don't compose.
  • §10 says MC's “nudges become turn-scoped reminders”, which §7.5 delivers as an operator-authority operator_message.
  • §6.3 says operator text must be static, but MC's nudges carry per-session numbers (hygiene percentage, counts).
  • §7.8 says in-run nudges are “class 2 data the engine applies”, but what decides an MC nudge is runtime pressure state that only the transform holds.
What exists today: MC's transform, the one live seam (§7.1), runs on every provider request, decides the nudges, and emits them as frozen units in the user-role tail, minted only on a pass that is already busting and replayed byte-identically afterwards [design authors, task Q&A]. The decision is in §7, row 14. Separately, §7.5's “re-sent verbatim after it clears” is undefined; the MC author doesn't know what it means either, so it is an open question for BROCA, who wrote §7.5.
“Tool added that was declared up front → tool change by reference.” §7.5 delivers such a tool by reference, which implies tools declared but not loaded. §12 says deferred tools (defer_loading) are not in v1. It's unclear whether reference delivery is v1 behaviour (and for which tools) or a v2 row.

6.3 The report's top three recommendations for r3 [C §6]

  1. Add G1, a preset switch on request, activated at the next run boundary. The most common Gap (6 of 20); fits existing machinery (table alternates, §6.5 activation, §7.5 delivery). Resolve Q1 at the same time.
  2. Settle §12 “Asking the user” and G4 (start a run and continue) as host services with WAL records. Ask-user in 5 plugins, wake or continue in 5.
  3. Specify G2 (per-run user-authority context) and Q4 (the class 3 rule vocabulary). Memory plugins are the largest category in both lists; without G2 they misuse operator text (engram) or vanish from history after one run. Q4 decides whether guard plugins are declarative data or excluded code.

9. Gaps found while explaining

Places where the sources are ambiguous, contradict each other, or don't give the reason for a rule. None were filled in; the text above follows the design and flags each one.

  1. Activation authority. D §6.5 “Prefrontal decides when a session activates” vs PH “activation IS the module flipping its declared epoch”. Already the report's Q1.
  2. Discovery path. PH says the engine discovers plugin modules “from the catalog's hooks manifest section — SUBC's lane defines that section”. D §5.1–§5.2 says no new manifest roles: discovery is capabilities.provides plus extension.describe. Not stated whether the hooks manifest section is superseded or still carries class 3/4 artifacts.
  3. Ordinary later sends (clarification for r3). It follows from D §6.5 and §7.2 step 5 that a non-activating send reuses the frozen record and never calls extension.describe, but no sentence says so explicitly.
  4. Activation with a module down (clarification for r3). Unstated; this page assumes the activation is skipped and retried at the next boundary.
  5. Host notes vs last-module append (clarification for r3). D §6.4 should say “last in precedence, including host notes”; this page presents it that way.
  6. Reference delivery vs deferred tools. D §7.5 “tool added that was declared up front → tool change by reference” vs D §12 “Deferred tools … not in v1”.
  7. MC nudges: contradiction. D §10 (nudges become operator-authority turn reminders) vs §6.3 (operator text static; nudges carry numbers) vs §7.8 (in-run nudges are class 2 data, but only the transform sees pressure). Decision in §7 row 14.
  8. “Re-sent verbatim after it clears” (D §7.5) is undefined. Question for BROCA.
  9. AFT “edit presets”. D §10's line is left over from an earlier example. This page assumes all four presets replace the slots and reader is narrowed by the profile. Questions for AFT in §7 row 16.
  10. Modules and classes. D §6.1 “modules never map themselves to classes” vs AFT's table “Classes” column and R9's “declare their most restrictive class”.
  11. Principle 5 wording. “History rewrite is one exclusive, privileged slot” predates r2's reduction-owner-plus-pipeline split (D §6.6).
  12. Restricted tier for module code. D §8 applies AFT's tool-level trust split to “module code”; what it restricts for a third-party module's own process is unstated.
  13. Incomplete refusal list. D §7.2 step 3 omits R7 closure and R8 host-capability refusals.
  14. Two build stagings. D §13 vs PH commit staging; interleaving unstated.
  15. Costs. The design seldom states a rule's cost; most costs in §4 are marked derived.
  16. Reductions and the cache. The design doesn't state the cache effect of a reduction itself (step 5 above); it only guarantees protected spans and replay determinism.
  17. Class 2 tail decoration has no authority row in D §8. Already the report's G2.
  18. “Third-party persona” naming (owner ruling). D §10's “third-party persona (declarative file)” is really a declarative preset carrying static system text; personas are Prefrontal's. The heading uses a word the design reserves for the caller.
  19. G7 reclassified (owner ruling). The report tags G7 as (b) and counts it in its §4 totals; per owner ruling it is out of scope. The report itself is unchanged.
